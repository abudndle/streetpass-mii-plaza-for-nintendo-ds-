# DS / 3DS cross-system visitor relay contract

Status: **proposed bridge contract; no native 3DS StreetPass interoperability**.

## Goal

A DS/DSi-originated visitor may traverse DS/DSi and a compatible 3DS
companion, and a 3DS-originated visitor may travel in the opposite direction.
Every hop must retain origin identity, encounter nonce, and permitted Mii
appearance, while preventing duplicate delivery and unauthorized redistribution.

## Trust boundary

The existing 80-byte SPDR v1 packet is an independent homebrew protocol:
it includes a 64-byte SPDS record, origin timestamp, CRC32, and a bounded
remaining-hop count. It does **not** contain an original Mii appearance,
a console-origin discriminator, cryptographic sender authentication, or
Nintendo CECD StreetPass metadata. A CRC detects accidental corruption,
not malicious modification. A 3DS companion cannot be described as
native StreetPass simply because it reads this format.

A compatible 3DS application must implement SPDR v1 separately or negotiate
a versioned bridge format. The DS receiver must reject unknown versions,
malformed lengths, invalid CRCs, and exhausted hop budgets. Neither side
may claim to be the originating console when forwarding an existing visitor.

## Required bridge payload for appearance-aware exchange

- Stable origin-system type (DS/DSi/3DS), separate from transport hop.
- Stable origin identifier and encounter nonce, not regenerated by relays.
- Bounded remaining hops, decremented exactly once per forwarding system.
- Consent/copy/redistribution permissions separate from local Mii selection.
- Versioned avatar payload with validated size and integrity, independent of
  Nintendo's proprietary on-air CECD encryption.
- Explicit provenance and replay policy; do not infer trust from CRC alone.

## Implementation milestones

1. Validate DS-to-DS relay on physical hardware, including duplicates and
   TTL expiry; do not treat successful host tests as radio validation.
2. Research the documented stock-3DS StreetPass Relay Point / SpotPass service flow and determine whether a lawful independently operated relay service can interoperate with unmodified retail firmware. Do not assume a generic access point or custom HTTP endpoint is sufficient.
3. Implement and test the service adapter only after the required request/response protocol, authentication and payload contract are established from public documentation and authorized hardware observations.
4. Test DS -> relay service -> stock 3DS Mii Plaza and the reverse direction on real consoles. A homebrew companion may be an optional fallback but does not satisfy the stock-3DS requirement.

## Current constraints

SPDR v1 has a four-forward budget, allowing up to five receiving systems.
The present DS radio transport sends profile metadata, not full Mii appearance.
A separate full-Mii SD visitor bundle exists but is not a radio avatar
transport. Any 3DS companion or native CECD receiver is **not implemented**.
